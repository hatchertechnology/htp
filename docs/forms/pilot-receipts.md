# Pilot receipt reconciliation — draft, read-only

This is a proposed operator-only procedure, not deployed or approved for hosted use. No function, endpoint, role, grant, migration, or activation is added. An existing authorized operator needs sufficient SELECT access to the four named tables, including the private tombstones; do not grant it merely to run this query. The statement returns `visibility_unavailable` if row-level security is active for the current role on any of the four relations. It does not grant or bypass access. Independently verify the effective role, SELECT privileges, relation identity and full visibility for the actual target; if these cannot be established, stop. Permission errors are unknown, never absence. The columns needed are `websites(id, owner_id)`, `website_forms(id, website_id)`, `website_form_responses(website_id, form_id, submission_id)` and `website_form_submission_tombstones(form_id, submission_id)`. An existing operator may have broader raw access than the status output; this proposal adds no access, and a future narrowed operator capability needs separate review.

After an uncertain submit, independently authenticate and revalidate the exact website and current owner, and obtain the exact form and submission IDs through the authorized incident workflow. Do not search, enumerate, interpolate values into SQL, or print bindings, request content, values, hashes, response IDs, hostnames, credentials, or raw database errors. Execute `supabase/operations/forms-pilot-receipt.sql` as a single parameterized statement with exactly four non-null UUID bindings in order: website, owner, form, submission. Reject missing or malformed bindings before execution; use an operator channel that supports actual bound parameters and suppresses parameter logging. A fresh read-only transaction with bounded statement timeout and a single statement gives one consistent snapshot. Run on the primary, not a lagging replica. Verify target, query identity, transaction/read-only behavior, role/RLS, underlying relation definitions and provider logging/error handling before any proposed hosted use. Do not paste a query with real identifiers into an audit trail or a client that logs parameters.

The only successful output is one status:

- `visibility_unavailable`: RLS applies to the current role on at least one required relation; stop and do not treat other evidence as visible.
- `active_receipt`: an active response for this exact scope was visible at the snapshot.
- `deleted_receipt`: a tombstone for this exact form/submission was visible at the snapshot.
- `ambiguous`: both were visible; stop and investigate, with no automated retry.
- `scope_unavailable`: current owner/site/form relationship did not match, including missing site or form; stop. This intentionally does not disclose which condition occurred.
- `no_receipt_observed`: neither was visible in this snapshot. This is **not evidence of non-acceptance**, including after gate removal, while a request is active or in flight, after cascading deletion, retention changes, incomplete visibility, or an uncertain transaction. Never infer failure or retry solely from this result.

A receipt proves a row or tombstone existed at the snapshot, not that a particular payload matched, who submitted it, delivery, notification, or the outcome of another attempt. A later transfer, deletion or commit can change the result. Read-only MVCC does not wait for in-flight accept/delete/transfer or make the result final. Establish the original request/session outcome and quiescence independently; if unavailable, preserve uncertainty. SQL errors, timeouts, disconnects, inconsistent target, visibility uncertainty, or unexpected results are `unknown`, not absence. Do not blind-retry or change approval, grants, or data to resolve ambiguity. Form or website cascade deletion can remove the evidence; the historical owner cannot use current ownership as proof of past ownership. This query neither serializes privileged actors nor proves historical identity.

Before deployment, obtain independent review of exact SQL and target schema/constraints, operator identity and effective access, private binding and logging behavior, transaction/snapshot semantics and primary routing, plus a separately approved incident procedure. The public regression `python3 supabase/tests/fixtures/forms-pilot-scope/receipt-pg17.py` needs Docker and the pinned PG17 image; it builds a network-isolated disposable database from checked-in migrations and synthetic fixtures. It uses actual migration function bodies and synthetic auth helpers, not hosted ACLs or ownership. Its SQL PREPARE and synthetic EXECUTE literals test parameter semantics, not a real provider client’s wire bindings or logging. It does not validate hosted privileges, provider transport, concurrent DDL, all races or a retention policy.
