# Authenticated Forms ingress prototype

This is a local API prototype, not a deployable edge forwarder or release approval. `HTP_ROLLOUT_FORMS=true` remains a separate, default-off gate. With `FORMS_INGRESS_MODE` absent or `fly`, the existing `FORMS_TRUST_FLY_PROXY=verified` behavior is unchanged. Select `FORMS_INGRESS_MODE=edge` independently; an unknown mode or incomplete edge configuration fails closed even if the Fly flag is set. Edge mode requires `FORMS_EDGE_KEY_CURRENT`, and optionally `FORMS_EDGE_KEY_PREVIOUS`, each exactly 64 lowercase hex characters encoding 32 independently generated cryptographically random bytes. Invalid configured keys disable ingress. The API accepts exactly one `X-HTP-Edge-Auth` containing either key and exactly one `X-HTP-Client-IP` containing a single IP address. It compares fixed-size keys in constant time. It never uses Fly or forwarded headers in edge mode. Authentication and identity failure return the existing opaque 503 before any database call. The existing shared client/global and form limits, origin checks, CORS, responses and receipt semantics apply unchanged.

The intended trust boundary is a provider-hosted edge forwarder with a server-side secret, connecting to one fixed HTTPS HTP origin with normal certificate and hostname verification, redirects disabled, and no user-controlled destination. TLS must protect the entire path to the component that checks the secret; if TLS terminates upstream of the API, the remaining hop must also be authenticated and protected. The edge must obtain the visitor IP from a provider-authenticated connection property, not a request header. It must discard all incoming identity, authentication, forwarding and hop-by-hop headers, construct a fresh request with only the public contract headers needed for Forms, and set these two headers itself. Never return or log the credential, raw identity, or request body; redact them at every proxy, tracing and error layer. The browser never receives the secret. Keep secrets in provider secret storage and distribute independent random values through an authorized secret-management process.

**Hosted dependency:** no provider or topology has been verified here. Before activation, select and independently verify a provider's exact client-IP provenance, header stripping and overwrite behavior, ability to protect and verify the entire origin connection, fixed destination, secret isolation, log redaction, and behavior on direct origin access. A bearer credential authenticates its holder, not the provider or the end user; a stolen key permits identity forgery. Ensure all traffic reaching this mode passes the authenticated boundary, and confirm the API and intermediaries do not log headers. Local synthetic tests establish none of these hosted properties. There is no automatic fallback to Fly identity when the edge is unavailable.

Forward only the intended Forms path and methods; bound body size, connection time, concurrency and total time consistently with the API's 20,000-byte body and 25-second deadline. Disable automatic retries of POST and do not redirect. Return the API status, body and relevant CORS, cache and retry headers without inventing a receipt. A timeout is an unknown outcome: the client may retry the identical submission ID and payload under the existing contract; ordinary HTML submissions without a client ID cannot safely deduplicate an ambiguous retry. OPTIONS can be retried only with a small fixed bound. Protect the origin credential from client responses and errors.

For rotation, provision a new random key as current on every API instance while retaining the old key as previous, switch all forwarders to the new key, verify convergence through separately authorized operational procedures, then remove the previous key from all instances. Do not leave a previous key indefinitely. For compromise, disable ingress and revoke the compromised key immediately; do not use the overlap to preserve availability. Coordinate the separate IP-hash key rotation as described in the Forms contract, since it resets effective client windows.

The activation SQL fixtures only rehearse host-proof grants and notification hold behavior; they do not establish ingress identity, TLS, provider configuration, hosted grants, or production readiness. All existing pilot scope, service-only RPC, migration, notification and rollback prerequisites remain in force. The test-only synthetic forwarder in the API unit tests builds a fresh allowlisted request and injects a synthetic IP and key in process; it is not a production forwarder and does not test TLS or a provider.
