# Website forms — contract

Status: **implemented and CI-covered; pilot only.** Host verification, form definitions, public ingress, the owner inbox, response management and the notification pipeline are implemented and exercised by the Forms CI workflow (`.github/workflows/forms-pr.yml`). The dashboard pilot is live for the approved pilot website only. **Notifications are implemented but not configured in production** (owner decision D3, 2026-11-26): the pilot runs inbox-only, with no recipients, no notification scheduler and no delivery credentials. This document is the behavior contract; it is not a release approval. Adding websites, enabling notification delivery or opening public rollout requires the separately reviewed activation steps below.

## Owner setup: host verification

A signed-in website owner starts a DNS proof with `begin_form_host_verification(website_id, hostname)`. It returns a random TXT value for `_htp-verification.<hostname>`. Publish that value exactly, then call the authenticated `form-verify` function with `host_id` and the token after `htp-verification=`. The verifier resolves TXT over HTTPS (Cloudflare DoH), checks the current challenge and expires it after 24 hours. Starting a new challenge immediately invalidates the old proof. Each additional exact host requires its own proof. A website may retain up to 64 host records and an account up to 256 across all its websites; existing records remain rotatable when already at or above a limit, but new hosts are rejected. An account may start or rotate 60 challenges in a ten-minute fixed window shared across its websites; excess attempts must wait. Rejected starts do not invalidate existing proofs. No automatic host deletion is performed; resolving a full quota requires a separately reviewed cleanup path.

## Form definitions and field flags

`save_website_form` accepts website ID, optional existing form ID, stable key, name, JSON field definitions, active flag and verified host IDs. Supported types are `text`, `email`, `telephone`, `multiline`; each field has `key`, `label`, `kind`, `required` and `max_length`. Keys `submission_id` and `website` are reserved. Keys must match `[a-z][a-z0-9_]{0,63}`, labels are 1–100 characters, `max_length` is 1–5000, and a form has 1–32 fields. Updates are scoped to the authenticated owner and website; active forms require at least one verified host.

The pilot form's field flags follow owner decision D4 (2026-11-26): **name, email and message are required; phone is optional.** The flags are set through `save_website_form` with the same keys and limits. A required field rejects an empty value with `validation_failed` and a per-field entry in `fields`.

## Visitor ingress and origin checks

The visitor endpoint is `/public/forms/<uuid>` on the HTP API and requires a configured verified exact HTTPS browser origin, or an HTTPS Referer when Origin is absent. A missing or invalid Origin and Referer is rejected with 403 `origin_required`. The check accepts one Origin or one Referer header (never both duplicated), the literal `null` is refused, and the URL must be HTTPS with no userinfo, no explicit port and a host; an Origin must be a bare origin (path `/`, no query or fragment), while a Referer may carry a path. The host is then matched against the form's configured verified origins; a mismatch is 404 `form_unavailable`. Nondefault ports, HTTP and sibling hosts are not accepted. These headers and CORS are browser abuse controls, not visitor identity; non-browser callers can forge them. Additional operational rate and abuse protection is required before rollout.

A missing-Origin rejection still consumes both admission windows (see below), because it is charged before the origin check. CORS preflight (`OPTIONS`) succeeds with the reflected origin only when the origin is allowed, and a verified-origin preflight succeeds even when the form window is exhausted so the subsequent POST can expose its 429.

## Submission handling

AJAX POST accepts a flat JSON object containing the configured fields and a client-generated UUID `submission_id`; `website` is a honeypot and must be empty or absent. Ordinary `application/x-www-form-urlencoded` POST uses the same flat names. When an ordinary form omits `submission_id`, the server creates one, so an ambiguous retry cannot be deduplicated. Integrations requiring retry safety must generate and reuse an identifier for the same submission. The identifier is scoped to one form and retained with the response. Reuse with different data returns 409. Successful JSON is `{"ok":true,"duplicate":false}` or `{"ok":true,"duplicate":true}` after durable database commit. Plain HTML posts currently display the same JSON response. Invalid fields return 422 with `error: validation_failed` and `fields`; honeypot submissions return 422 `spam_rejected`; oversized bodies return 413; form-wide exhaustion returns 429; unavailable storage returns 503. The database enforces a shared limit of 300 requests per existing form per 10 minutes, including preflight, missing-origin and honeypot requests, plus a limit of 100 non-duplicate validation attempts per form per 10 minutes. For a verified-origin POST that reaches the API, both form ingress and validation-window 429 responses expose `Retry-After: 600`. The independent API client/global limiter still charges and caps preflights. These form-wide limits can be exhausted by spoofed requests and do not protect against unknown-form traffic; they are not a substitute for trusted network-level controls.

## Retention and deletion

Responses are retained indefinitely until an owner explicitly deletes them; there is no automatic retention scheduler. Deletion removes response content and associated delivery history, retains a private submission ID and value hash indefinitely to prevent duplicate retries, and waits for in-flight notification jobs. Website deletion is refused while responses exist or a notification is sending. Once responses have been explicitly removed, deleting the website also removes its empty form configuration, associated hosts and retained idempotency hashes; the deleted form endpoint no longer accepts retries. Renaming a website pauses its forms and invalidates its host proofs without deleting responses.

## Notifications: implemented, not configured in production

The notification pipeline is implemented end to end: recipient verification (`request_form_recipient` plus the emailed one-time link and `/forms/confirm` page), delivery jobs with lease-based claims, the Postmark `form-notifications` worker, owner notification APIs and the dashboard recipient/delivery UI. Production is not configured for delivery (owner decision D3, 2026-11-26): the pilot runs inbox-only, with zero recipients, no `htp-form-notifications` cron schedule, and the delivery worker and owner notification flags unset. Recipient verification emails are sent only by the `form-notifications` worker; while delivery is unconfigured, queued verification jobs are not sent, and the dashboard's empty delivery state does not imply delivery capability.

Owners can add recipients, who must confirm a one-time emailed link before receiving notifications. Disabling a recipient cancels pending jobs; an already in-flight email may still arrive. The worker marks provider acceptance as sent, known rejection as failed (retryable), and timeouts or expired leases as uncertain (not automatically retried; an owner can explicitly resend a response notification after acknowledging that a duplicate email is possible). Verification requests with uncertain delivery require a new verification request. This status does not prove mailbox delivery. CSV quoting and formula neutralization apply in the inbox export.

## Delivery worker (unconfigured in production)

Notification delivery requires `FORMS_DELIVERY_ENABLED=true` in the Edge worker environment. With the flag absent or set to any other value, the worker returns `503 delivery_disabled` before claiming a job; with the flag on but the sender, Postmark token, secret or verify URL missing, it returns `503 delivery_not_configured`. Configure `FORMS_SENDER`, `POSTMARK_SERVER_TOKEN`, `FORMS_NOTIFICATION_SECRET`, service-role credentials, and the matching scheduler Vault secret. Set `FORMS_VERIFY_URL` to the dashboard's HTTPS `/forms/confirm` URL without credentials, a trailing slash, query, or fragment. The worker sends text-only messages with Postmark link tracking disabled so confirmation fragments are preserved. Response notifications use the validated visitor address as Reply-To.

Deploy the worker with delivery disabled and leave the scheduler unscheduled until the database claim fence and pilot shutdown path are verified. Verify the confirmation page and API, sender, queue health, and provider outcomes with bounded test data before scheduling recurring delivery. Each invocation claims at most one job. For a stop, close database admission, stop the scheduler, and allow already-issued leases to record their outcomes before disabling or removing the worker. Closing admission cannot retract a provider request already underway. An ambiguous provider outcome requires provider-side verification before any explicit resend.

## Deployment and rollback

Production rollout requires all Forms migrations (`20261122000000` through `20261210000000`, including the host-challenge quota, pilot-scope and notification-fence migrations), three Edge Functions (host verification, recipient confirmation and notifications), notification scheduler, verified Postmark sender and service credentials kept only server-side, provider and network controls, independent review, and live end-to-end verification. Disable the public API route first and preserve response and idempotency data. Reverting to the prior Edge architecture would require deploying its removed submission function and credential; do not restore that public path without separately approved and verified ingress protection. Do not drop tables containing inquiries as a rollback shortcut.

Rollback procedure: stop the `htp-form-notifications` cron job and public API ingress first; run `supabase/rollbacks/20261122000000_forms_disable.sql` to revoke form RPC access while retaining data. Once the cause is resolved, `supabase/rollbacks/20261122000000_forms_restore.sql` restores those grants; verify database ownership and delivery state before restarting functions and the scheduler. These scripts assume all form migrations are installed; verify on an isolated database before use.

## Ingress identity and admission

Ingress is disabled unless a trusted identity mode, `SUPABASE_URL`, `FORMS_SERVICE_KEY`, and `FORMS_IP_HASH_KEY` are configured. The legacy mode requires `FORMS_TRUST_FLY_PROXY=verified`; the separately selected authenticated edge mode and its default-disabled Cloudflare forwarder are described in [authenticated ingress](authenticated-ingress.md) and [forwarder](forwarder.md). The rollout gate remains independently off by default. The Fly flag is a deployment assertion, not automatic proxy verification. A 25-second overall request deadline bounds the full admission, body and RPC sequence; a timeout does not prove an acceptance transaction rolled back, so retry the identical ID and payload. The API directly calls the service-only form RPCs; this branch contains no deployable submission Edge Function. API admission uses a service-only shared ten-minute window of 100 requests per keyed client and 10,000 requests globally, with a maximum of 10,000 client keys; a limiter failure fails closed. Verify Fly proxy exclusivity and header overwrite, service-only RPC access, multi-instance behavior, key rotation, CORS, migration and rollback before activation. Local fixtures do not verify live proxy identity. Before rollout, reverify that `form-submit` is absent. If a function exists, stop and reconcile its identity and ownership before any removal; never delete an unexpected function automatically.

Rotate the API service credential and IP-hash key consistently across instances during a coordinated pause; changing the hash key resets effective per-client windows. Preserve database rows and use disable/restore scripts as a single transaction each.

Host-challenge rollout: migration `20261128000000_forms_host_challenge_quota.sql` installs the capped function and restores the two authenticated owner grants. Apply it only in a separately verified atomic migration transaction, after the earlier forms migrations and a staging hold that prevents the original 002 grants from becoming callable. Before the quota migration exists, the updated forms restore script refuses to regrant access; this guard checks local object markers and is not a substitute for independent exact-definition and effective-role verification. Never apply the older unguarded restore script during the hold. Even the updated restore script regrants all forms RPCs, including management and status; do not run it while any independent grant hold remains. Existing hosts and responses must be retained; rollback must not re-expose the uncapped 002 function. Test lock ordering, staged grant behavior, quota limits and denial UX before activation.

## Browser CORS and failure contract

Dashboard host verification invokes `form-verify` directly through Supabase Functions. The function allows browser CORS for `https://htp.hatchtech.dev`, matching the configured auth site URL. For a different environment, set the Edge Function's `NUXT_APP_ORIGIN` to the exact dashboard origin (scheme, host and port, without a trailing slash), matching the Nuxt convention. This is function runtime configuration and must be provisioned separately; it does not change hosted configuration by itself. Origin is not authorization: POST retains bearer authentication, the caller-scoped challenge RPC and service-only completion. Requests without Origin continue to work. Supabase's default JWT verification remains enabled; errors produced before the handler by the provider may have different CORS behavior and are not covered by the local fixture.

Browser failure contract for visitor ingress: API client/global admission and other failures before API origin verification do not reflect Origin; cross-origin `fetch` reports a network/CORS failure, including when a preflight receives a non-2xx response. A direct HTTP caller can inspect the API 429 and Retry-After, but JavaScript must not depend on those being readable. The client must preserve the fields and submission ID, report that acceptance is unconfirmed, and retry the identical payload and ID when appropriate. API-generated POST errors after verified origin checks may expose their status; verification, proxy, network, and preflight failure can remain opaque. Neither an opaque failure nor a retry establishes acceptance; only `ok:true` does.

## Local verification

To exercise the browser path locally, install the web dependencies and run `cd apps/web && node tests/fixtures/check-form-verify-browser.mjs` with Deno on PATH. It uses the pinned Supabase JS SDK, Chromium, the real handler, and disposable mocked DNS and storage; it does not contact Supabase or change DNS.

Example ordinary HTML (replace the endpoint with the one shown for the form):

```html
<form action="https://API_HOST/public/forms/FORM_UUID" method="post">
  <label>Name <input name="name" required></label>
  <label>Email <input name="email" type="email" required></label>
  <label>Phone <input name="phone" type="tel"></label>
  <label>Message <textarea name="message" required></textarea></label>
  <label hidden>Leave empty <input name="website" tabindex="-1" autocomplete="off"></label>
  <button>Send request</button>
</form>
```

The fields must match the saved form definition. For AJAX generate a UUID for each new inquiry, hold it across ambiguous failures, POST the flat values and `submission_id` with `Accept: application/json`, and only clear values and generate a new UUID after a successful `ok: true` response. Disable the submit button while a request is in flight. Trigger analytics only once after confirmed acceptance, including after a successful replay, and make the confirmation say an inquiry was received; it does not book a visit. A page reload needs persistent client state if retry deduplication must survive navigation. The normal HTML example has no client-generated UUID and cannot deduplicate a retry after an ambiguous failure.
