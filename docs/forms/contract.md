# Website forms — work in progress

This is an implementation increment, not a release approval. Operational abuse controls, pilot integration and live verification remain incomplete. Notification delivery and deletion require further review and live verification. Do not deploy or advertise the feature as complete.

A signed-in website owner starts a DNS proof with `begin_form_host_verification(website_id, hostname)`. It returns a random TXT value for `_htp-verification.<hostname>`. Publish that value exactly, then call the authenticated `form-verify` function with `host_id` and the token after `htp-verification=`. The verifier resolves TXT over HTTPS, checks the current challenge and expires it after 24 hours. Starting a new challenge immediately invalidates the old proof. Each additional exact host requires its own proof.

`save_website_form` accepts website ID, optional existing form ID, stable key, name, JSON field definitions, active flag and verified host IDs. Supported types are `text`, `email`, `telephone`, `multiline`; each field has `key`, `label`, `kind`, `required` and `max_length`. Keys `submission_id` and `website` are reserved. Updates are scoped to the authenticated owner and website; active forms require at least one verified host.

The visitor endpoint is `/public/forms/<uuid>` on the HTP API and requires a configured verified exact HTTPS browser origin, or an HTTPS Referer when Origin is absent. A missing or invalid Origin and Referer is rejected. Nondefault ports, HTTP and sibling hosts are not accepted. These headers and CORS are browser abuse controls, not visitor identity; non-browser callers can forge them. Additional operational rate and abuse protection is required before rollout.

AJAX POST accepts a flat JSON object containing the configured fields and a client-generated UUID `submission_id`; `website` is a honeypot and must be empty or absent. Ordinary `application/x-www-form-urlencoded` POST uses the same flat names. When an ordinary form omits `submission_id`, the server creates one, so an ambiguous retry cannot be deduplicated. Integrations requiring retry safety must generate and reuse an identifier for the same submission. The identifier is scoped to one form and retained with the response. Reuse with different data returns 409. Successful JSON is `{"ok":true,"duplicate":false}` or `{"ok":true,"duplicate":true}` after durable database commit. Plain HTML posts currently display the same JSON response. Invalid fields return 422 with `error: validation_failed` and `fields`; honeypot submissions return 422 `spam_rejected`; oversized bodies return 413; form-wide exhaustion returns 429; unavailable storage returns 503. The database enforces a shared limit of 300 requests per existing form per 10 minutes, including preflight, missing-origin and honeypot requests, plus a limit of 100 non-duplicate validation attempts per form per 10 minutes. A 429 response supplies Retry-After: 600 for the ingress window. These form-wide limits can be exhausted by spoofed requests and do not protect against unknown-form traffic; they are not a substitute for trusted network-level controls.

Responses are retained indefinitely until an owner explicitly deletes them; there is no automatic retention scheduler. Deletion removes response content and associated delivery history, retains a private submission ID and value hash indefinitely to prevent duplicate retries, and waits for in-flight notification jobs. Website deletion is refused while responses exist or a notification is sending. Once responses have been explicitly removed, deleting the website also removes its empty form configuration, associated hosts and retained idempotency hashes; the deleted form endpoint no longer accepts retries. Renaming a website pauses its forms and invalidates its host proofs without deleting responses. Owners can add recipients, who must confirm a one-time emailed link before receiving notifications. Disabling a recipient cancels pending jobs; an already in-flight email may still arrive. The worker marks provider acceptance as sent, known rejection as failed (retryable), and timeouts or expired leases as uncertain (not automatically retried; an owner can explicitly resend a response notification after acknowledging that a duplicate email is possible). Verification requests with uncertain delivery require a new verification request. This status does not prove mailbox delivery. CSV quoting and formula neutralization apply in the inbox export. Deployment requires all form migrations `20261122000000` through `20261122000900`, four Edge Functions, notification scheduler, verified Postmark sender and service credentials kept only server-side, provider and network controls, independent review, and live end-to-end verification. Existing functions remain unchanged on rollback; disable the new public function first, preserve response data, then revert application code. Do not drop tables containing inquiries as a rollback shortcut.

Notification deployment requires `FORMS_SENDER`, `FORMS_VERIFY_URL` (the HTTPS `/forms/confirm` page), `POSTMARK_SERVER_TOKEN`, `FORMS_NOTIFICATION_SECRET`, service-role credentials and the matching scheduler Vault secret. Send responses use the validated visitor email as Reply-To, never as From. One worker invocation claims one job. Confirm the sender, scheduler, queue health, provider outcomes and rollback with bounded test data before enabling notifications. An ambiguous provider outcome is not automatically retried; verify with the provider before deciding whether to resend.

Example ordinary HTML (replace the endpoint with the one shown for the form):

```html
<form action="https://API_HOST/public/forms/FORM_UUID" method="post">
  <label>Name <input name="name" required></label>
  <label>Email <input name="email" type="email" required></label>
  <label>Phone <input name="phone" type="tel"></label>
  <label>Message <textarea name="message"></textarea></label>
  <label hidden>Leave empty <input name="website" tabindex="-1" autocomplete="off"></label>
  <button>Send request</button>
</form>
```

The fields must match the saved form definition. For AJAX generate a UUID for each new inquiry, hold it across ambiguous failures, POST the flat values and `submission_id` with `Accept: application/json`, and only clear values and generate a new UUID after a successful `ok: true` response. Disable the submit button while a request is in flight. Trigger analytics only once after confirmed acceptance, including after a successful replay, and make the confirmation say an inquiry was received; it does not book a visit. A page reload needs persistent client state if retry deduplication must survive navigation. The normal HTML example has no client-generated UUID and cannot deduplicate a retry after an ambiguous failure.

Rollback procedure: stop the `htp-form-notifications` cron job and public function ingress first; run `supabase/rollbacks/20261122000000_forms_disable.sql` to revoke form RPC access while retaining data. Once the cause is resolved, `supabase/rollbacks/20261122000000_forms_restore.sql` restores those grants; verify database ownership and delivery state before restarting functions and the scheduler. These scripts assume all form migrations are installed; verify on an isolated database before use.


Ingress is disabled unless `FORMS_TRUST_FLY_PROXY=verified` and `FORMS_RECEIVER_URL`, `SUPABASE_URL`, `FORMS_SERVICE_KEY`, `FORMS_INGRESS_SECRET`, and `FORMS_IP_HASH_KEY` are configured. The Fly flag is a deployment assertion, not automatic proxy verification. The receiver requires the matching ingress secret for every request including OPTIONS; do not expose it to visitors. API admission uses a service-only shared ten-minute global and keyed client window; a limiter failure fails closed. Verify Fly proxy exclusivity and header overwrite, direct receiver rejection, multi-instance behavior, key rotation, CORS, migration and rollback before activation. The receiver currently has no overlapping-secret rotation and requires a coordinated pause for rotation. Local fixtures do not verify live proxy identity.
