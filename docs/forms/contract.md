# Website forms — work in progress

This is an implementation increment, not a release approval. Notification delivery, explicit response deletion, operational abuse controls, pilot integration and live verification remain incomplete. Do not deploy or advertise the feature as complete.

A signed-in website owner starts a DNS proof with `begin_form_host_verification(website_id, hostname)`. It returns a random TXT value for `_htp-verification.<hostname>`. Publish that value exactly, then call the authenticated `form-verify` function with `host_id` and the token after `htp-verification=`. The verifier resolves TXT over HTTPS, checks the current challenge and expires it after 24 hours. Starting a new challenge immediately invalidates the old proof. Each additional exact host requires its own proof.

`save_website_form` accepts website ID, optional existing form ID, stable key, name, JSON field definitions, active flag and verified host IDs. Supported types are `text`, `email`, `telephone`, `multiline`; each field has `key`, `label`, `kind`, `required` and `max_length`. Keys `submission_id` and `website` are reserved. Updates are scoped to the authenticated owner and website; active forms require at least one verified host.

The visitor endpoint is `/functions/v1/form-submit?form=<uuid>` and requires a configured verified exact HTTPS browser origin, or an HTTPS Referer when Origin is absent. A missing or invalid Origin and Referer is rejected. Nondefault ports, HTTP and sibling hosts are not accepted. These headers and CORS are browser abuse controls, not visitor identity; non-browser callers can forge them. Additional operational rate and abuse protection is required before rollout.

AJAX POST accepts a flat JSON object containing the configured fields and a client-generated UUID `submission_id`; `website` is a honeypot and must be empty or absent. Ordinary `application/x-www-form-urlencoded` POST uses the same flat names. When an ordinary form omits `submission_id`, the server creates one, so an ambiguous retry cannot be deduplicated. Integrations requiring retry safety must generate and reuse an identifier for the same submission. The identifier is scoped to one form and retained with the response. Reuse with different data returns 409. Successful JSON is `{"ok":true,"duplicate":false}` or `{"ok":true,"duplicate":true}` after durable database commit. Plain HTML posts currently display the same JSON response. Invalid fields return 422 with `error: validation_failed` and `fields`; honeypot submissions return 422 `spam_rejected`; oversized bodies return 413; form-wide exhaustion returns 429; unavailable storage returns 503. The current database limit is 100 non-duplicate validation attempts per form per 10 minutes; it does not cover all rejected traffic and is not a substitute for network-level controls.

Responses are retained indefinitely in the current increment; there is no deletion UI or retention scheduler. Website, form and host foreign keys restrict deletion to protect inquiries. No user-accessible mechanism to erase responses has been added yet. Owner-scoped response reads and status updates exist; no notification recipients, delivery status, retry worker, or email sender are implemented. CSV quoting and formula neutralization apply in the inbox export. Deployment requires the three form migrations, both Edge Functions, service credentials kept only server-side, provider and network controls, independent review, and live end-to-end verification. Existing functions remain unchanged on rollback; disable the new public function first, preserve response data, then revert application code. Do not drop tables containing inquiries as a rollback shortcut.
