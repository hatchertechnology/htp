# Default-empty pilot gate: release and recovery requirements

`20261201000000_forms_pilot_scope.sql` is a draft, not an activation. It introduces an empty approved `(website_id, owner_id)` gate, preserves existing owner authorization, and revokes the eight owner RPCs from PUBLIC, anon and authenticated rather than granting access. It replaces the existing function bodies only when their expected source hashes, `SECURITY DEFINER` flags and fixed search paths match. Its role checks include effective privileges reachable through membership, including PostgreSQL 17 `MAINTAIN`. A rejected installation rolls back its changes. It inserts no approved site, does not start a worker or scheduler and does not provision a secret.

The migration affects existing service requests: with an empty approval table, acceptance, origin lookup and verification completion deny every site. Existing owner RLS reads and stored responses, idempotency tombstones, recipients and delivery jobs remain intact; pending or in-flight notification jobs are not stopped by this gate. Origin and acceptance are separate transactions, and acceptance independently rechecks the gate. Removing approval prevents new acceptance and blocks same-ID retries until reapproval. An unavailable response is not proof that the original submission failed. Removal also blocks the gated owner status, recipient and response-deletion functions. Before activation, design and review bounded receipt reconciliation, data export/deletion and emergency recipient-disable access.

The proposed `supabase/rollbacks/20261201000000_forms_pilot_scope_disable.sql` revokes the three service entry points and the eight owner writes, checks membership-reachable effective denial, and retains the gate, function bodies, data, jobs and ledger. It is fail-closed, not an automatic re-enable; a conflicting inherited grant aborts the transaction. The fixture SQL in `supabase/tests/fixtures/forms-pilot-scope/` is **not a hosted rollback or grant procedure**. Real recovery requires a separate target-specific reviewed procedure that first stops ingress, coordinates all service callers, drains or reconciles in-flight verification and notification jobs, confirms effective owner and service holds, preserves data and ledger history, and verifies the outcome before any independently approved re-enable. Never run the broad Forms restore while holds remain.

Only a separately approved administrative identity may add or remove a site/owner pair. This migration defines no operator-facing grant or row. Before any later approval, independently review the identity's permissions, role membership, credential handling, auditing, concurrency/lock order and unknown-commit recovery. A user-editable claim, session marker or UI flag is not authorization. Ownership transfers invalidate the old pair; locks make approval removal wait for guarded in-flight transactions, but production load and all competing operations still require verification.

The adopted branch chronology is Forms `20261201000000_forms_pilot_scope.sql`, then policy `20261202000000_seosmith_remediation.sql`, then surfaces `20261203000000_audit_event_queue.sql` and `20261203000001_audit_operational_hooks.sql`. The policy and surfaces branches remain unmerged and their migrations unapplied; integration must reconcile their owners, review the exact combined heads and confirm the final release order before any separately authorized deployment. Recheck the canonical hosted ledger, exact quota/function/owner/role/default-ACL/event-trigger fingerprints and effective PUBLIC/inherited/SET ROLE rights immediately before that deployment. The migration's source/security checks are narrower than that preflight and do not prove hosted role ownership, full catalog state, provider migration/ledger atomicity, or live API routing. Confirm real `auth.jwt()`/`auth.uid()` claims and function execution under the actual provider; the local fixtures substitute synthetic auth helpers. Verify the Fly trusted peer boundary, API CORS, service-only calls, queue behavior and absence of an unexpected public submit Edge function separately. Reconcile rather than delete any unexpected function.

Notifications are a separate release decision. The local scheduler specifies 30 seconds while sequential worker budgets total 35 seconds plus overhead; verify timing, cancellation, queue capacity and uncertain-delivery reconciliation before any scheduler or mail activation. No live DNS, pilot entry, credential, scheduler, email or deployment is authorized by this document.
