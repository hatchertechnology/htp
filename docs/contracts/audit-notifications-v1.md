# Proposed audit and operational notification contract v1

Status: **disabled prototype; no producer or transport is enabled**. The TypeScript classifier and SQL processor are candidate implementations, not authorized production producers. H03 currently computes bounded lifecycle at read time, and H04's mutable work records are not an event source. Stored-report GETs and exports must remain read-only.

## Source and identity

The receiver must transactionally enqueue a processing item with each newly committed, verified worker receipt, keyed by website, binding generation and immutable delivery ID; a repeated identical receipt must not enqueue twice. Imports are not trusted worker observations and do not trigger automatic alerts. A separate privileged processor reads immutable report bytes and a fixed prior compatible baseline, stores its semantic version, source and baseline delivery IDs, source locators, scan times and evidence versions with each event, and atomically records results and completes its work item. A crash or retry must not create duplicate events. It must never modify receipts or emit from a GET. Do not enable the processor until it has a bounded, indexed, authoritative history and paired fixture conformance with H03.

Scope comparisons by website, exact current FQDN, binding generation, schema 2 / evidence contract 1, policy digest, engine and ruleset versions, entity ID, rule, rule version and validator version. Event v1 candidates require explicit eligible, completed checks. A pass to fail produces a new failure; call it reopened only with a verified comparable earlier failure; fail to fail emits only when technical severity increases. Absent, unknown, ineligible, not-attempted, or incompatible observations do not imply a pass or change. Unverified imports, schema 4 and legacy reports do not emit. The classifier requires strictly increasing scan times; ties, late receipts, ambiguous baselines, missing history and unverifiable provenance are held for review, never silently reordered or retroactively used to rewrite delivered events. A bounded search cannot prove all-history reopening. Store the reason that processing was held, separately from event records.

Deduplicate an event by `(semantics_version, website_id, current_delivery_id, entity_id, rule, kind)` under a database unique constraint; persist the chosen baseline and any earlier evidence used. Use structured columns or collision-safe encoding. Lock per site and binding during baseline selection; duplicate deliveries, concurrent workers and retries must converge. If a late receipt changes the historical interpretation, keep the original event and delivery immutable and create an explicitly versioned correction only after a separate correction policy is defined; v1 holds rather than inventing one.

## Operational failures

Google and Bing report jobs have `failures` and `last_error`; repository sync has `last_error`. They are mutable operational state, not durable failure history. A production producer must capture a failure episode transactionally at the authoritative job transition from healthy to failed, identify the website, provider, job and a generated episode ID, and close it on a confirmed successful transition. Retries in the same episode deduplicate; a later failure after confirmed recovery gets a new episode ID. Classify bounded error codes without exposing raw upstream messages or credentials. Binding changes, deletion, manual resets and missing rows are not confirmed recovery. Explicitly specify which failure classes and persistence threshold are actionable before enabling. Existing failed jobs need a separately reviewed bootstrap policy; do not synthesize historical events from current state.

## Delivery and rollout

Keep events separate from per-recipient/channel deliveries. An enabled, authorized destination creates one delivery keyed by event, destination and channel; atomic lease, expiry, retry/backoff and a bounded dead-letter state support crash recovery. Recheck recipient authorization and destination configuration before sending. A stable provider idempotency key should be used where supported; without provider idempotency an ambiguous timeout cannot guarantee exactly once, so expose uncertainty and reconcile instead of blindly resending. Do not include credentials, untrusted HTML or raw provider errors in payloads. Failed delivery must never roll back a receipt or lose the event. There is no existing general notification transport in this repository; no external sends are enabled by this proposal.

Roll out schema and owner-scoped reads first with emission and delivery disabled, backfill only with an explicit policy, validate receiver and producer against shared positive/negative fixtures and controlled late/concurrent deliveries, then enable generation and finally a configured transport. Rollback disables generation and delivery, retains receipts, event records and delivery state, and restores previous readers; do not delete queued evidence. Authorization tests must include guessed IDs and cross-account access. Fixture success does not establish production readiness; confirm migrations, receiver compatibility, delivery behavior and recovery on the deployed system before claiming it.

## H03 indexed-history dependency

H03 draft `7ade251bd6d67595a9e5c840aaeb2c23aa87049a` provides a rebuildable evaluation index and paginated, owner-scoped history. It marks legacy, unsupported, pending, absent and unknown evaluations explicitly. It is a read contract, not a consistent snapshot or event producer: late inserts can change a cursor walk, and pre-existing audits require explicit backfill. An event worker must use a transactionally stable snapshot and a serialized per-binding ordering policy, exhaust relevant history, and hold whenever an index marker or evidence is unavailable. Do not derive notification eligibility from the bounded dashboard window. The draft also notes that full-history classification remains unfinished, so this foundation must remain disabled until both contracts and the producer are independently validated.

## Disabled prototype and release blockers

The additive 20261203000000 migration contains an explicitly gated receipt queue and processor prototype. A service caller must open a READ COMMITTED transaction, call `audit_event_snapshot_lock()` in its own statement, then call `audit_event_process()` with a valid lease before committing. The processor checks the lock and holds unknown, incompatible, tied, late or oversized input; it caps a binding to 100 saved runs and each compared finding list to 1,000. The global `SHARE` lock blocks receipt inserts until the transaction ends. It is not authorized to enable until target-PostgreSQL contention, large-report processing, concurrent receipt/import, index/backfill, and lease-recovery tests are complete. This is a deliberately conservative prototype, not full-scale H03 equivalence.

A snapshot only closes the current transaction, not the past: an older receipt can arrive after an event was persisted. Two possible release policies are (1) an authoritative producer watermark/finalization contract that rules out earlier receipts for the processed interval, with explicit late-receipt handling, or (2) immutable correction events and an operator/delivery policy for correcting already-sent notifications. Neither contract exists today. Until one is specified and tested, keep processing and delivery disabled even when all local fixtures pass.

`audit_operational_completion` is a service-only hook called from lease-validated Google, Bing and repository completion paths in migration `20261203000001`; its operations gate defaults off. It accepts a small error-class vocabulary and deduplicates an open episode; reconnect, binding reset and other mutable job updates are not wired as recovery. It receives the verified completion outcome from the owning job function; an enabled hook failure rolls back that completion transaction and requires operational monitoring. Delivery records have no configured destination store, authorization recheck, sender, claim/retry implementation or transport; they must not be used to send messages. Event and episode reads use bounded keyset pages with paired timestamp/UUID cursors and explicit `has_more`. H04's draft work record uses the immutable delivery/finding index for work planning and is not a cross-run event identity or source of resolution events.

A local PostgreSQL 16.15 synthetic two-session check confirmed that the SHARE lock blocks a concurrent receipt insert and waits for an in-flight insert before a subsequent READ COMMITTED statement sees it. This is not a target-PostgreSQL benchmark or a complete transaction/concurrency proof.

A synthetic isolated Supabase PostgreSQL 17.11.0.004 check also confirmed the basic two-session lock behavior. Single samples using a stub index took 0.092 s for 100 saved runs × 100 evaluations and 0.626 s for 100 runs × 512 evaluations with 1,000 findings per run. These measurements omit competing load, real receiver/index/backfill behavior and production data; they are not release performance evidence.

A paired local PGlite test against H03 draft index and two validated immutable worker receipts confirmed an unchanged second receipt produced no event. The positive change fixture still uses synthetic index rows and must be replaced or supplemented with paired producer/receiver evidence before activation.

The forms draft `bb2e82901d1c2992c9cd7c5289b29b03d3342285` includes a Postmark worker and recipient verification, but its jobs and payload are form-specific and its reuse contract is not frozen. Its known-failure versus uncertain-outcome handling is relevant for a future shared delivery adapter; provider acceptance must not be described as mailbox delivery.
