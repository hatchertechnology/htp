# SEOsmith lifecycle comparison (read contract v1)

HTP reads immutable saved audit details; comparison does not start a crawl or change a report. The UI chooses a baseline by saved delivery ID; tied scan instants are not ordered. It loads at most ten contiguous runs already present in the history list, stopping at an incompatible run. First/last observed and reopened states describe that loaded window, not the entire retained history. The selection and lifecycle comparisons are computed on demand; the separately indexed finding and URL histories described below are not notification event streams. Individual URL results are limited to the first 100 on screen; large property values are abbreviated with pointers to the original reports. The source reports remain available for download.

For schema 2 / evidence contract 1, comparisons require matching summary comparison key, engine and ruleset and matching S01 policy digest. Each transition requires explicit eligible, completed pass/fail evaluations with the same rule and validator versions. A missing, omitted, unavailable, uninstrumented or unknown evaluation is `not_observed`, not a pass. A pass-to-fail is new only when the loaded history is complete and every earlier check is an explicit compatible pass. It is reopened only when a compatible earlier failure is followed by an explicit pass; otherwise its lifecycle state is not observed. A fail-to-pass is resolved; fail-to-fail is persisting or changed according to stored finding evidence. Earlier failures remain visible when later checks are unknown. First/last timestamps use the saved scan time and are bounded by the loaded window; they are not per-fetch timestamps. Per-rule coverage reports the producer's stored-entity denominator, attempted, not-attempted, attempt-unknown and unknown-outcome counts, and excluded (ineligible plus unknown eligibility); it does not count the unvisited web.

URL identity uses the S01 entity ID and exact stored URL. Available observations from both runs are required for changes; missing or unavailable observations are not removal. Response fields are compared when available; HTML metadata, body hash and link/relationship arrays require successful HTML on both sides and complete extraction. Missing optional fields remain unknown, not empty. Property values and JSON pointers reference the retained baseline/current reports. This does not invent S03 freshness, S05 link-context or S06 semantic-content evidence.

Legacy schema 1 retains the existing whole-run conservative comparison. Unknown future schemas are not comparable. The v1 read result is an HTP-side interpretation, not a changed SEOsmith wire format; the index migration is additive; no producer change or new receipt is required. S01 receiver support and validated v2 reports must exist before using this interpretation. No new production flag is activated by this code. Rollback restores the previous web build; retained reports remain unchanged and v2 receiver support must remain for retained v2 reports. S14 and other future contracts need separately versioned comparison semantics before use.

Release requires independent review of the exact revision, tests against retained v1/v2, partial and truncated producer fixtures, authorization and performance checks through real reads, and a receiver-first end-to-end canary with exact receipt/source preservation. Fixture tests alone are not production verification. Pagination of comparison changes, cross-surface integration and richer producer evidence remain follow-on work; do not close H03 on the basis of this bounded UI alone.

## Indexed finding history

Migration `20261125000000` adds a rebuildable index of explicit S01 evaluation records and one status marker per audit, with compact policy, version and rule-coverage metadata so history pages do not extract it from full report bodies. Inserts after migration populate the index transactionally; pre-existing rows remain `index_pending` until a privileged operator repeatedly runs `seosmith_lifecycle_backfill(50)` until it returns zero. This procedure is explicit, bounded, idempotent and never called by a read. For a known corrupt or incomplete marker, a privileged operator can call `seosmith_lifecycle_reindex(delivery_id)`: it locks the audit and atomically replaces only its index rows, preserving the original report and receipt; verify the rebuilt history and monitor impact. Evaluation index rows retain only the compact history projection; actual and expected evidence remains in the original report. The owner-scoped `GET /websites/{id}/seo/audits/lifecycle?entity_id=...&rule=...` pages all saved runs in descending `(scan_at, delivery_id)` order, up to 100 rows per page. Its v1 rows include delivery ID, scan time, policy/versions, rule coverage, evidence state and compact evaluation provenance. Actual and expected values are deliberately omitted from this bounded response (`evidence_values_omitted: true`); use the authorized immutable detail/download and source pointer to inspect them. Legacy, unsupported, pending, absent and explicitly unknown evaluations stay visible as unknown; none is a pass. The dashboard can load these pages from an entry and shows first/last failures and adjacent transitions among loaded rows, explicitly warning when earlier pages or unknown evidence remain. Failure changes use a SHA-256 digest of the canonical PostgreSQL JSONB finding, not a normalized content or business-impact score. A new versus reopened label requires all earlier relevant rows to be available and compatible, or a known earlier matching failure; missing pages and unknowns remain not observed. Equal scan instants do not establish ordering. This endpoint does not classify lifecycle events, rewrite reports, or initiate collection.

Deployment is migration/index and receiver/read support first, then API and web; verify privileges and backfill in bounded batches with operational monitoring, and verify all historical pending rows before using the index for an authoritative producer. Keep the additive index and receiver on rollback to avoid disrupting retained data; rolling back the web/API returns to saved detail reads. Benchmark maximum-sized report ingestion, index storage, backfill, paging and late arrivals on the target PostgreSQL version before release. Schema 4 remains unsupported until S14 is jointly specified and reviewed.

## Indexed URL history

The same migration indexes up to the S01 observation bound per run. The owner-scoped `GET /websites/{id}/seo/audits/url-lifecycle?entity_id=...` pages saved runs by exact S01 entity ID, with persisted `ingestion_source`, evidence state, source locator, and per-property SHA-256 digests. Indexed properties cover response status/type/redirect and, only for successful untruncated HTML, title, description, canonical/directives/language, body hash and word/DOM counts, headings, images, links, relationships, alternates, structured data and social metadata. Hashes represent stored JSONB values and can reflect array order; they are not semantic similarity or proof of indexability. Missing values, unsupported schema, blocked/unavailable pages and missing observations remain unknown. Compare only matching policy/engine/ruleset and strictly ordered scan times. The original reports supply actual values and graph evidence; no source is promoted from import to worker based on report claims. The dashboard shows one page plus one boundary row at a time to keep memory bounded, preserving per-field unknowns and source pointers.

Synthetic PostgreSQL 17 timing evidence and its limitations are recorded in `supabase/benchmarks/lifecycle-pg17/README.md`; it does not replace the target-database, maximum-size, concurrency, backfill and live receiver release checks above.
